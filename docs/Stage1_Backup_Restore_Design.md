# Stage 1: 完全バックアップ・復元 設計

## 目的

作品データ（localStorage）と画像データ（IndexedDB）を一体として保全し、端末故障・ブラウザデータ消失・アプリ更新時に復元できるようにする。既存のJSONバックアップとの互換性は維持する。

## 現状の保存領域

- localStorage: `aiclip_v02`（作品、シーン、アセットのメタデータ）
- IndexedDB: `AIClipStudioAssets`
  - `images`: 現在のアセット画像（key = assetId）
  - `assetImageVersions`: 差し替え前画像の履歴（versionId、assetId、blob、savedAt、reason）

## 採用するバックアップ形式

単一ファイルの非圧縮 TAR（拡張子 `.tar`）を採用する。画像BlobをBase64化せずバイナリのまま格納するため、JSON/Base64方式より余分なメモリと約33%のサイズ増加を避けられる。ZIP互換をうたわず、アプリ専用のmanifestを含むTAR形式として明示する。

アーカイブ構成：

```
manifest.json
data/projects.json
images/current/<assetId>.blob
images/history/<versionId>.blob
```

manifestには形式識別子、スキーマバージョン、作成日時、各ファイルのパス・サイズ・MIME type・対応IDを記録する。IDはパスとして安全な文字列か検証し、パストラバーサルを拒否する。

## 書き出し要件

1. IndexedDBの接続完了を確認する。未接続なら書き出しを開始しない。
2. localStorageの作品データをJSONとして取得し、構造を検証する。
3. IndexedDBの `images` と `assetImageVersions` を読み取りトランザクションで取得する。
4. メタデータ上の `hasImage` と実Blobの対応を検査し、不整合があれば件数と対象IDを表示して、ユーザーが中止または不完全バックアップを選べるようにする。
5. TARヘッダーとBlobをBlobパーツとして組み立て、Base64変換や巨大な単一ArrayBuffer化を避ける。
6. 完了したアーカイブのみダウンロードする。失敗時は不完全ファイルを完成品として表示しない。

## 復元要件（置換）

復元は既存データを置き換える破壊的操作なので、検証完了前に既存データを変更しない。

1. ファイルサイズ上限、TARヘッダー、manifest形式、重複パス、パス安全性、各エントリのサイズ、ID重複、MIME、Blob参照整合性を検証する。
2. manifestに記載された全エントリが実在し、余分・欠落・重複がないことを確認する。
3. 復元予定の作品数・シーン数・アセット数・現行画像数・履歴画像数をプレビューする。
4. 復元前の現行データを自動退避する。退避に失敗した場合は復元を開始しない。
5. 復元ジャーナルを記録し、IndexedDB側に復元世代マーカーを持たせる。localStorageとIndexedDBは別トランザクションなので、両者の更新を単一トランザクションと偽らない。中断・再起動時にジャーナルと世代マーカーから旧状態へ戻すか、新状態の確定を完了する回復処理を設ける。
6. IndexedDBの画像・履歴をトランザクション内で置換し、完了後に作品JSONを確定する。いずれかが失敗した場合はロールバックまたは起動時回復を行う。
7. 復元後に件数、ID、画像参照を再検証し、成功を表示する。

## 安全策

- 現行のJSONバックアップ／JSON読み込み機能を削除・変更せず、旧バックアップを引き続き読み込めるようにする。
- 「追加・統合」と「完全復元（置換）」をUI上で明確に分ける。
- 復元前に対象端末・現在の作品数・復元後の作品数を表示し、明示確認を必須にする。
- 破損・未知バージョン・容量不足・IndexedDB quota・transaction abort時は既存データを維持する。
- 画像が多い場合のメモリ負荷を避けるため、TAR生成・解析はBlob sliceを基本とし、巨大なArrayBufferへの一括展開を避ける。
- 既存DBの `images` と `assetImageVersions` を削除・改名しない。
- DBバージョンアップが必要な場合は、既存storeを保持したまま追加storeのみ作成する。

## テスト計画

### 正常系
- 画像なし作品、画像あり作品、複数画像、履歴画像ありの書き出し・復元
- 復元後の作品・シーン・アセット・画像・履歴の件数とID一致
- 日本語名、長い作品名、空欄フィールド
- 旧JSONバックアップの読み込み互換

### 異常系
- TARヘッダー破損、manifest欠落、未知schema version
- ファイル欠落、余分なファイル、重複パス、重複ID、パストラバーサル
- manifestサイズと実データサイズの不一致
- Blob欠落、MIME不一致、hasImage参照不整合
- 容量不足、IndexedDB transaction abort、復元中のタブ終了・再読み込み
- 復元前退避に失敗した場合に復元を開始しないこと

### 実機
- iPad Safariで大容量画像を含む書き出し・読み込み
- iPadの「ファイル」アプリへの保存・再選択
- バックグラウンド移行・画面ロック後の復帰
- ストレージ空き容量が少ない場合の失敗表示

## 実装順序

1. TAR writer/readerを独立した関数として実装し、形式単体テストを行う。
2. manifest生成とデータ整合性検査を実装する。
3. 完全バックアップ書き出しを追加する。
4. 復元ジャーナル・世代マーカーによる回復機構を実装する。
5. 復元プレビューと完全復元を追加する。
6. 旧JSONとの回帰テスト、iPad Safari実機テストを行う。

## 完了条件

- バックアップに作品データ・現行画像・画像履歴がすべて含まれる。
- 復元前の検証・退避が完了しない限り既存データを書き換えない。
- 復元途中の失敗・再起動後も旧状態または新状態のどちらかに整合して回復する。
- 旧JSONバックアップの読み込みを壊さない。
- iPad Safariで正常系・異常系を確認する。

## 実装状況追記（2026-11-24）

- IndexedDBをversion 3へ更新。既存の `images` / `assetImageVersions` storeを維持し、復元時の退避用 `restoreBackupImages` / `restoreBackupHistory` と `restoreJournal` を追加。
- 完全バックアップTARの読み込み後、ユーザー確認を経て置換復元を開始する。
- 置換前に現行Blobを同一IndexedDB readwrite transaction内で退避し、ジャーナルを記録してから現行storeを入れ替える。TAR内の画像はFile.slice()でBlobとして渡し、画像全体をArrayBufferへ一括展開しない。
- IndexedDB更新完了後にlocalStorageの作品データを更新する。localStorage更新または確定処理に失敗した場合、退避storeから旧画像・履歴を戻し、旧作品JSONを復元する。
- 起動時に未完了ジャーナルを検出した場合は旧状態へ回復してから作品画面を表示する。
- 復元成功時のみ退避storeとジャーナルを削除する。
- 現段階の静的JavaScript構文検査はPASS。ただし、ブラウザ実行、IndexedDB transactionの異常系、タブ終了・再起動後の回復、iPad Safari実機は未検証。実データでの運用前に必須の検証項目。
